# RC2 critique verification — 2026-09-09

**Reviewer:** Astra. **Source inspected:** `ebeaf72` on `release/v1.0-candidate`, plus Kevin's supplied, untracked `critique-2026-09-09.md`, read in full before the audit. The linked GitHub page could not be retrieved through the web tool; this review uses the complete local copy and the repository evidence it names. No runtime source, assets, project settings or release package changed during this planning audit.

The central finding stands: engineering completion and visual acceptance were conflated. The critique gives useful priorities, but two of its four pivotal technical premises need correction. Node counts are evidence of implementation choices, not a reliable count of visible effects.

## Additional corrections and omissions

- **Lighting:** there is no shared engine lighting setup, but the picture is not wholly without a lighting model. `solar_body.gdshader:57` samples a rotating sphere and applies limb darkening, spots and a procedural corona. `release_view.gd:288` shades trusses directionally; `:320` selects hot/working/cold band textures, two band thicknesses, depth faces and HP-dependent lamps. These are disconnected approximations. The star's hard rim and weak transfer of its light onto hardware are visible in the opening image. An emissive star being `unshaded` is appropriate; removing that flag indiscriminately would be a mistake.
- **An unanticipated architectural risk:** `release_view.gd:34` creates a cached fortress SubViewport with its own `World2D`, usually updating only on invalidation. A core light in the parent world will not automatically relight geometry inside that separate world. Full-frame cache invalidation could erase RC2's performance recovery. T-081 must prove lighting, normals, cache invalidation and final glow composition together; T-087 must preserve the result when it changes layout and viewport sizing.
- **Collapse:** the moving eight-line debris and actual shake are too weak for a ring catastrophe. Debris admission at `release_view.gd:151` comes from `broken_wedges`; `collapsed_rings` only triggers the same breach sound. This is a concrete missing event-to-presentation distinction. Reduced motion does disable existing phase progression/shake/debris, so the claim that it advertises a nonexistent feature is overstated. This audit has not watched a newly captured collapse sequence; T-083 requires one.
- **Audio:** `game_audio.gd` has seven runtime-generated cues, an eight-second looping ambience, eight reusable voices and a shared 130 ms shot throttle. There are no authored WAV/OGG/MP3/FLAC/AIFF/Opus assets under `assets/`. The cues include harmonics, seeded noise and a victory chord, so “seven sine beeps” is reductive. No composed score, weapon-specific mix, directional threat design or rich event vocabulary exists. The asserted 90-second fatigue threshold is an opinion, not a measured listening result. A shared throttle can discard audible events; it does not delay simulation hits.
- **Theme/layout:** the 73-line theme is real; line count is not a quality metric. Existing buttons have hover/focus states, and the live core ProgressBar has local style overrides. Menus already use VBox/HBox/Scroll/Grid/Tab containers internally. The outer 2560×1440 composition and many view positions are hard-coded, however. Simply enabling `canvas_items` will not solve reading order, usable-map framing or all pointer transforms. Preserve UI scale as accessibility rather than delete it as a supposed workaround. The live Alt labels still use a fallback font, confirming a typography gap on an actual shipping path.
- **Resolution:** RC2 already renders at 2560×1440 and opens at 1920×1080. The reviewed art fixture is 1440×810. Output resolution, asset canvas resolution and apparent size on screen are three different quantities. Increasing PNG dimensions cannot repair a 4.4 px silhouette. Responsive native rendering and physical-pixel size floors are separate requirements.
- **Elite rules:** D-120 already allowed elite/boss emissive rank accents; D-128 already allowed five distinct cold-family identity hues. The critique's blanket “no glow” description confuses standards with elites and the stricter old production template. D-131 now authorizes broader elite/Assembler treatment explicitly; standards and the wider D-120 direction remain restrained. In the close image, Foundry is visibly broader and more distinct than the weakest Tunneler/Transfer/Breacher grouping.
- **Current crowd behavior:** `release_view.gd:489` provides a 4-unit screen floor for standards and 9 for elites, plus non-color outline glyphs; outer stage scaling can shrink those below that many physical display pixels. `data/balance/release.json:61` caps live machines at 128, while `testing.json` retains 1,000. The canonical fortress capture has 120. The new gate must distinguish a 128-machine shipping case, an 800+ live stress case and the exact 1,031-sprite historical diagnostic. Increasing the shipping cap is not authorized by this pass.
- **Minimap:** it is faint, but not empty of status. It draws broken/critical/brownout/relay indicators and supports navigation. Its native 264 px size yields outer radius 126 and about 8.19 px per band at twelve rings, about 6.14 physical px at 1080p; the critique's radius 72 is not the current native layout. Its 0.045/0.14 fill alpha values are correctly cited. Readability still needs a timed check at actual window sizes.
- **Results evidence:** `capture_release.gd:40` uses a durable fixture; `:61` sets elapsed time to 900 before forcing the victory view. The 0 kills and 1000.0M values are fixture output, not proof that ordinary gameplay wins without combat. That capture proves screen rendering, not a complete natural run. Result hierarchy and repeated credits are visibly weak. T-093 requires actual full-duration run evidence as well as labeled diagnostic results.
- **Run decision:** `src/gameplay/run_rules.gd:6` is 900 seconds; spec §§1–2 say endless and radius climb/fall. This was disclosed in `docs/RELEASE-REPORT.md:28` and `docs/RELEASE-CANDIDATE.md:7`, so “not recorded anywhere” would be wrong. The missing formal spec-level decision and approval trail are real. D-129 fixes that now, without rewriting the spec or pretending prior approval existed.
- **Regression count:** retained RC2 `presentation-v2/test-summary.json` contains **42 suites, all passed**, and there are 42 `test_*.gd` suite files now. The critique's 39 is an older aggregate. Preserve all 42 and any added suites; do not lower the baseline to 39. This is inspection of retained results, not a claim of a new test run.
- **Release scope:** “feature-complete” does not establish Steam activation, commercial quality, real-player balance acceptance or supported minimum hardware. Prior reports leave these limits explicit. This pass must not silently claim those gates passed.

## Visual assessment and release consequence

I inspected the actual start, opening, fortress and victory captures as well as both T-079 images above. The broad presentation criticism is justified: small default switches undermine the menu, startup framing ignores the usable map area, distant combat is dominated by markers, and victory gives more area to a transaction table than to the place the player built. The star has considerably more form and motion than a flat disc, but the fortress does not convincingly share its illumination.

T-079 was not passed by later engineering tests or by adopting some of its candidate assets. The release-candidate label was allowed to outrun the visual gate. D-132 now makes failed required acceptance gates release-blocking; D-133 makes spec departures traceable before implementation. RC2 remains historical evidence, not an accepted commercial release. All new work is awaiting plan approval.

## Planning implications

1. First deliver the small toggle/arrow correction, then retire rendering and cache risk with comparable native measurements.
2. Test Compatibility glow against Mobile rather than mandate a renderer migration on a false premise. A backend sample exceeding the agreed 10% envelope stops progression and goes to Kevin.
3. Prove ring collapse as an early vertical slice before the broad layout rewrite. Freeze its integration interface so layout does not discard it.
4. Parallelize isolated audio, elite asset work and LOD helpers; serialize all shared presentation-file integration. Fix layout before adding screen motion.
5. Keep the full T-079 asset matrix in scope: elites are not its only failed subjects. Structure/terrain seating and readability belong in T-089, elite identity in T-092, and final closure in T-093.
6. D-130 was not supplied in Kevin's original message. After the omission was raised, Kevin resolved it during planning: develop a plan using free online AI audio generation. `docs/audio-generation-plan.md` now specifies the shortlist and commercial-use admission checks; there is no paid budget.
