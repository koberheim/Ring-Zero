# T-013 targeting performance delivery

The automatic combat API and gameplay rules are unchanged. `WeaponRules.step` derives each supplied target's world position once per call, retaining only local transient vectors. Returned target records still contain cloned PolarPosition objects. Weapons continue to read shared updated target HP, so earlier same-step kills affect later selection.

Small data-driven target caps use an exact ordered bounded selection instead of sorting every eligible target. Once full, the selection rejects a candidate only when it ranks after the current worst member by the existing distance/ID comparison. All targets remain considered, and existing range/arc checks still run. The algorithm crossover is 16 selected targets; it is not a gameplay cap. Larger configured caps use the original general full-sort approach. Neither path changes distance calculations, tie ordering, tolerances, hit order, damage, rewards, or cooldown behavior.

Validation: **219 weapon checks, zero failures** on pinned Godot 4.7.2. This retains all 56 accepted checks and adds 54 independent reference scenarios plus isolation checks. The reference deliberately ranks all living targets with a full sort and repeated polar conversions, then filters range/arc and takes the requested cap. It shares no optimized selection/caching helpers. Scenarios exercise caps 1/5/16/17/80/250, arcs 1/90/360, tuned ranges, varied polar rings/bearings/fractions, exact-distance ties with unordered IDs, dead targets, multiple weapons, broken wedges, same-step kills, subsequent calls and cooldowns. Comparisons assert exact hit arrays/order/damage, kill IDs, rewards, cooldown dictionaries, and every returned target field. Input state/targets/cooldowns, mutable positions, and nested target metadata remain isolated.

The unchanged `tests/performance/benchmark_crowds.gd` was run before and after the implementation. Each capacity used three warmups and ten measured samples, with no early stop. Values below are microseconds for ready volleys.
