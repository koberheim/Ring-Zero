## Prioritized corrections before enabling the complete roster

1. **P1 — Playable runs do not enable Phase 9.** `src/presentation/live_view.gd:103` creates the simulation with only the third boolean true. `src/gameplay/live_simulation.gd:78` defaults Foundry, Transfer, Sapper, Breacher and Assembler to false. Their descriptors/admission paths therefore never execute in the normal live entry point. Reproduction: start the ordinary view, inspect all enable flags, then survive past each configured arrival. Distinguish implemented/tested pure and isolated runtime systems from playable roster integration. Preserve legacy test factories while providing an explicit complete-roster run configuration.

2. **P1 — Transfer after its single hop bypasses normal inner-ring defenses.** `live_simulation.gd:939-956` directly chooses wall-or-wedge beneath `hop_cell`; it never consults normal exposed-before-wall routes or `TerrainRules.is_debris_blocking`. D-107 (`DECISIONS.md:3025`, resolution immediately before D-108) requires normal behavior after exactly one skipped ring. Reproduction: two intact rings; Transfer hops past ring 2 at wedge 1; put a wall on ring 1/w1 and leave ring 1/w2 exposed. It attacks that wall rather than taking the approved detour. Replace the wall with Debris Field: it damages the protected wedge directly. The shared graph excludes its legitimate landing cell because the skipped ring remains intact, so fixing this requires explicit reachable landing-boundary treatment, not merely calling `route_for` on an invalid source or globally opening the skipped ring to everyone.

3. **P1 — Post-hop Transfer gains further instantaneous inward travel.** In the same helper, a broken next-inner wedge causes position to become `PolarPosition.new(inner, wedge, 0, .5)` before `_advance_machine` receives the entire unchanged available time (`live_simulation.gd:950-956`). That is another 96 world units without travel time; the branch after its own wedge destruction similarly assigns the inner node immediately. Reproduction: hop past ring 2 with ring 1/w1 already broken, use a slow Transfer, compare consecutive radii/core attack time. It jumps from radius 192 to 96 and can attack core immediately instead of spending 96/speed seconds crossing the gap. Preserve only the one approved hop; subsequent travel must obey speed, shadow and time accounting. The initial hop also returns without spending/using remaining tick time (`:524-530`); its intended instantaneous-versus-whole-tick timing should be made explicit in the correction contract.

4. **P1 — Assembler computed growth lacks finite/integer guards.** Schema allows finite nonnegative `assembler.growth_damage_per_stack` and `growth_hp_per_stack` (`balance_profile.gd:133-134`), while `_assembler_growth_multiplier`, `_grant_assembler_growth` and attack multiplication (`live_simulation.gd:575-585`) perform unchecked multiplication/addition. Lifecycle validation checks only integer/nonnegative stack count (`:839`). Reproduction proposal: valid profile growth damage 1e308, existing Assembler growth_stacks=2 and normal finite DPS at core contact. The multiplier becomes infinity, attack can commit core loss rather than return an atomic error. A MAX_INT stack count can wrap when another wedge is consumed. HP growth overflow may be caught later by combat validation, but core-loss ticks skip combat, so that is not a complete guarantee. Validate computed prospective growth/damage and fail before committing, including on the core-loss path; retain unchanged state, IDs already admitted/released, counters, events and positions on failure. No cap or balance change is needed to fix numeric validity.

5. **P2 — Relay recovery is headless-only and HUD presence is not relay health.** Gameplay provides `quote_rebuild_relay`/`rebuild_relay` (`live_simulation.gd:265-276`), but the presentation search has no rebuild caller. `live_view.gd:630` emits `relay_active = not relay.is_empty()`; destroyed relays intentionally retain the presence marker and have relay_hp=0, so `ring_status_hud.gd:83` still draws them as active. Reproduction once Sapper is enabled: destroy a relay without collapsing any wedge, observe brownout with an apparently active marker and no Rebuild Relay command. Wire health/brownout and recovery using gameplay quotes, not presentation pricing or relay-destruction rules. This is a functional integration dependency, not final-art work.

## Rule attribution and composition requiring explicit contracts

- **Assembler collapse growth:** D-110 Option C says every wedge/wall/occupant personally destroyed grants permanent own growth. Current code grants the directly broken seventh wedge and all swept occupants/walls, but not the remaining five intact wedges set to zero during that same collapse (`live_simulation.gd:616-636`). The test at `tests/gameplay/test_live_simulation.gd:1030-1050` explicitly expects two stacks with one swept occupant. Decide/document whether collateral collapse wedges count as personally destroyed; do not change that test silently or present its existing interpretation as separately approved. Retained occupants on a lone broken wedge are not destroyed and should not be deleted or credited merely to simplify counting.
- **Destroyed-relay Sapper behavior:** current `:595-599` returns without damage when relay HP is already zero, so the Sapper camps harmlessly until the relay is rebuilt or topology changes. D-108 specifies relay targeting/loss consequence, but not the next objective after a dead relay. Document whether this is intended; it is not evidence that Sapper should suddenly attack wedges or ignore intervening rings.
- **Transfer landing topology:** latest source `:301-303` already exempts a hopped Transfer at its hop_cell from ordinary open-cell terrain-placement validation. The earlier provisional concern that it blocks every unrelated terrain command is withdrawn. A correction still needs an explicit no-trap/reachability policy for this exceptional boundary, including placement/repair near its landing route, rather than broadly exempting its eventual surface path.
- **Complete roster composition:** individual elite fixtures and pairwise capacity ties exist (`test_live_simulation.gd:691-1084`); the inspected factory calls do not exercise all six special types together. Add a mixed-roster fixed-seed/configuration integration scenario with shared capacity, exact-time ties, same-tick relay/wall/wedge losses, ability kills, collapse and forced downstream failure. The current admission order is Tunneler, Foundry, Transfer, Sapper, Breacher, Assembler, normal on ties (`live_simulation.gd:782-808`); retain/document it deliberately in the run contract.

## API recommendations for Phases 10 and 11

`docs/FULL-GAME-TEST-PLAN.md:93-109` calls for meaningful doctrine/loadout/mutator variety before persistent progression. No run-configuration, meta/save or result service was found in the current src file inventory. These are pending phases, not Phase 9 omissions.

1. Introduce a validated, independently copied `RunConfiguration` with schema/content version, stable configuration ID, seed, doctrine ID, loadout ID, sorted unique mutator IDs, explicit enemy roster, and any scenario/ring-limit choice. Resolve all effects into a fresh validated BalanceProfile/startup descriptor before constructing live state. Keep legacy `LiveSimulation.create` defaults compatible or adapt them through a named legacy factory; stop adding positional booleans to the playable call site. Expose a read-only resolved configuration snapshot for results and reproduction. Decide modifier composition order, incompatibilities and access validation in the contract.
2. Move authoritative totals into gameplay/session state. Current run kills live in `live_view.gd:29`, increment from tick events at `:151` and cast events at `:517`, and reset on view retry. A headless run currently has elapsed time but no durable total-kill/result ledger. Track committed weapon and ability kills separately plus total, earned energy separately from remaining bank, max owned/reclaimed ring milestones, and approved challenge facts. Failed/ended steps must not add totals. Commands must update the same ledger exactly once without relying on UI event consumption.
3. Provide a finalized immutable `RunResult` keyed by a unique run ID, including configuration/content version and seed, termination reason, authoritative counters and reward inputs. Finalization is idempotent. Distinguish defeat, abandonment, simulation error and debug/test runs; define eligibility before Phase 11 pays anything. Pure reward calculation should accept a validated result and progression policy, not live nodes or presentation labels.
4. Persistence consumes a result transaction by run ID once and atomically writes both awarded balance and consumed-ID marker. Upgrade/unlock spending similarly stages ownership/currency together. Define corrupt-file recovery, schema migration/version rejection, settings separation and explicit reset behavior. No mid-run save should be inferred from the need to persist completed-run progression. Keep equal-access test configurations available so grind does not mask variety balance.

Recommended sequence: fix Phase 9 gameplay/landing and computed-value defects; add named complete-roster configuration and mixed-roster tests; expose relay recovery feedback/command; implement configuration composition and contrasting equal-access runs; add authoritative result accounting; then persistent reward/spend transactions and between-run integration. Final art/animation is outside this sequence. The existing large-crowd performance shortfall remains unresolved; this audit performed no measurements and makes no frame-rate claim.
